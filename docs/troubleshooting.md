# Backstage Platform Engineering Troubleshooting Journal

This document records engineering problems encountered while building and hardening the AZ1600 Backstage Internal Developer Platform, together with the investigation process, root causes, fixes, and lessons learned.

The purpose is not only to document successful implementation, but also to preserve the reasoning behind failures and remediation decisions.

---

# 1. Golden-Path Dockerfile Was Difficult to Locate

## Symptom

While hardening the generated service template, the expected file:

```text
examples/template/content/Dockerfile
```

was not initially obvious in the editor.

## Investigation

The repository structure contains both the Backstage application itself and the content generated by the Software Template.

The generated-service files live beneath:

```text
examples/template/content/
```

rather than under the Backstage backend Dockerfile location:

```text
packages/backend/Dockerfile
```

## Resolution

The file was created and updated directly from the terminal:

```bash
mkdir -p examples/template/content

cat > examples/template/content/Dockerfile <<'EOF_DOCKER'
...
EOF_DOCKER
```

## Lesson

Backstage repositories commonly contain two different application contexts:

```text
Backstage platform runtime
        ↓
packages/backend/

Generated golden-path workload
        ↓
examples/template/content/
```

Changes must be applied to the correct runtime.

# 2. Golden-Path Container Originally Needed Runtime Hardening

## Goal

Generated services should start from secure platform defaults rather than requiring every application team to remember container-hardening practices.

## Changes

The template Dockerfile was hardened to include:

- fixed non-root UID/GID
- non-root runtime user
- container health check
- deterministic application path
- controlled file ownership

The generated Kubernetes workload was also strengthened with:

- readiness and liveness behavior
- restricted security context
- PodDisruptionBudget
- NetworkPolicy
- safer deployment defaults

## Validation

The generated image was built locally:

```bash
docker build \
  -t backstage-golden-path:test \
  examples/template/content
```

The runtime identity was checked:

```bash
docker run \
  --rm \
  --entrypoint id \
  backstage-golden-path:test
```

Expected:

```text
uid=10001(appuser) gid=10001(appgroup)
```

The service was then started using a read-only filesystem:

```bash
docker run \
  -d \
  --name backstage-golden-path-test \
  --read-only \
  --tmpfs /tmp \
  -p 18000:8000 \
  backstage-golden-path:test
```

Health was verified:

```bash
curl -s http://127.0.0.1:18000/health
```

## Lesson

Golden paths should encode platform security standards automatically.

A secure default generated by the platform is more reliable than documentation asking every developer to reproduce the same controls manually.

# 3. Jest Entered Watch Mode During Local Testing

## Symptom

Running:

```bash
yarn test
```

locally displayed:

```text
No tests found related to files changed since last commit.

Watch Usage
Press a to run all tests.
Press q to quit watch mode.
```

This initially looked like the tests had failed.

## Root Cause

Jest behaves differently when running interactively in a terminal.

Without CI mode it may enter watch mode and only evaluate tests related to changed files.

## Resolution

Use:

```bash
CI=true yarn test
```

This forces deterministic CI-style execution.

## Final Validation

```bash
CI=true yarn test
```

returned:

```text
Test Suites: 1 passed
Tests:       1 passed
```

## Lesson

Local interactive test behavior should not be confused with CI behavior.

For reproducible validation, explicitly run test commands in CI mode.

  packages/backend/src/index.ts

Validation was rerun:

```bash

```

and passed.

## Lesson

Formatting should be part of the normal validation pipeline rather than treated as cosmetic cleanup.

# 5. Prettier Cannot Format a Dockerfile Automatically

## Symptom

Running:

```bash
yarn prettier --write packages/backend/Dockerfile
```

returned:

```text
No parser could be inferred for file: packages/backend/Dockerfile
```

## Root Cause

The repository's Prettier configuration does not include a Dockerfile parser.

## Resolution

The Dockerfile was validated using Git instead:

```bash
git diff -- packages/backend/Dockerfile
git diff --check
```

## Lesson

Use the correct validation tool for each file type.

A formatter failing to recognize a Dockerfile does not mean the Dockerfile itself is invalid.

# 6. Production Authentication Should Not Use Guest Access

## Problem

Guest authentication is convenient for local development but is not an appropriate production authentication model.

## Implementation

Production configuration was changed to use GitHub authentication.

Environment-backed values are used for:

```text
AUTH_GITHUB_CLIENT_ID
AUTH_GITHUB_CLIENT_SECRET
```

The production configuration is checked in CI using harmless dummy values:

```bash
GITHUB_TOKEN=dummy \
BACKSTAGE_BASE_URL=http://localhost:7007 \
POSTGRES_HOST=localhost \
POSTGRES_PORT=5432 \
POSTGRES_USER=backstage \
POSTGRES_PASSWORD=dummy \
POSTGRES_DATABASE=backstage \
AUTH_GITHUB_CLIENT_ID=dummy \
AUTH_GITHUB_CLIENT_SECRET=dummy \
yarn backstage-cli config:check --strict \
  --config app-config.yaml \
  --config app-config.production.yaml
```

## Lesson

Development convenience settings and production identity controls should be explicitly separated.

# 7. Default Allow-All Authorization Was Too Permissive

## Problem

Backstage's default allow-all permission policy is useful for initial development but does not demonstrate production-oriented authorization.

## Resolution

The default policy was replaced with a project-specific permission policy.

The policy:

- uses authenticated Backstage identity
- checks ownership references
- restricts destructive catalog operations
- denies raw Kubernetes proxy access
- keeps normal portal discovery functionality available

## Security Principle

Authentication answers:

```text
Who are you?
```

Authorization answers:

```text
What are you allowed to do?
```

A production-oriented developer portal needs both.

# 8. Backstage Dependency Versions Were Not Uniform

## Symptom

Commands such as:

```bash
yarn why @backstage/backend-plugin-api
yarn why @backstage/plugin-permission-node
```

showed multiple compatible Backstage versions in the dependency graph.

## Investigation

Backstage packages often evolve at slightly different release cadences.

Transitive dependencies can therefore resolve to closely related but different package versions.

## Approach

Instead of forcefully deduplicating every Backstage package, changes were validated using:

```bash
yarn prettier:check
yarn lint:all
yarn tsc:full
CI=true yarn test
yarn build:backend
```

## Lesson

A dependency tree containing more than one package version is not automatically broken.

Compatibility must be validated through build, type, test, and runtime checks rather than by assuming all transitive versions must be identical.

# 9. Catalog YAML Can Be Syntactically Valid but Semantically Broken

## Problem

A YAML parser can confirm that catalog YAML is valid syntax while still allowing invalid Backstage relationships such as:

- missing owners
- missing systems
- missing domains
- missing APIs
- broken dependencies
- duplicate entity references

## Resolution

A custom offline validator was created:

```text
scripts/validate-catalog.mjs
```

It validates entities across:

```text
examples/platform-org.yaml
examples/platform-catalog.yaml
examples/template/template.yaml
```

Checks include:

- supported entity kinds
- `metadata.name`
- duplicate entity references
- owners
- systems
- domains
- provided APIs
- consumed APIs
- group membership
- typed dependencies

## Validation

```bash
yarn validate:catalog
```

produced:

```text
Catalog validation passed: 22 entities across 3 files.
```

## Lesson

Platform metadata should be validated semantically, not only syntactically.

# 10. GitHub Actions Trivy Release Could Not Be Resolved

## Symptom

GitHub Actions failed during job setup with:

```text
Unable to resolve action aquasecurity/trivy-action@0.33.1
unable to find version 0.33.1
```

## Root Cause

The GitHub release tag includes a `v` prefix.

The invalid reference was:

```yaml
uses: aquasecurity/trivy-action@0.33.1
```

## Resolution

The workflow was moved to a valid release reference:

```yaml
uses: aquasecurity/trivy-action@v0.36.0
```

The generated golden-path CI template was updated as well.

## Lesson

A dependency version can exist while still being unusable if the Git tag/reference syntax is incorrect.

Always validate exact GitHub Action release identifiers.

# 12. vm2 Vulnerability

## Finding

Trivy found vulnerable `vm2` versions in the production image.

Dependency inspection showed:

```text
typescript-json-schema
└── vm2
```

Initial version:

```text
3.11.5
```

## First Attempt

```bash
yarn up -R vm2@3.11.7
```

failed:

```text
Ranges aren't allowed when using --recursive
```

## Resolution

The correct Yarn 4 command was:

```bash
yarn up -R vm2
```

The dependency resolved to:

```text
vm2@3.12.2
```

## Lesson

With Yarn 4, recursive upgrades operate from existing dependency ranges.

An explicit range cannot be supplied together with `--recursive`.

# 13. Vulnerable undici Versions

## Finding

Trivy identified multiple vulnerable `undici` versions.

Dependency inspection:

```bash
yarn why undici
```

showed copies introduced by packages including:

- Backstage CLI tooling
- Module Federation
- jsdom
- node-gyp
- urllib

## Safe Recursive Upgrades

Where dependency ranges permitted it:

```bash
yarn up -R undici
```

moved versions such as:

```text
6.26.0 → 6.29.0
7.27.2 → 7.30.0
```

## Exact-Pinned Module Federation Version

One dependency used an exact:

```text
undici@7.24.7
```

A targeted root resolution was added:

```json
"resolutions": {
  "undici@npm:7.24.7": "npm:7.30.0"
}
```

## Validation

```bash
yarn why undici
```

confirmed vulnerable `7.24.7` copies were gone.

## Lesson

Prefer normal semver-compatible upgrades first.

Use targeted resolutions only when a parent package pins an otherwise compatible vulnerable version.

# 14. urllib Vulnerability Was Fixed Through the Parent Package

## Finding

The chain was:

```text
@backstage/backend-defaults 0.17.2
└── infinispan 0.12.0
    └── urllib 3.27.3
```

The vulnerable `urllib` release required a newer major version.

## Wrong Approach Avoided

We did not force:

```text
urllib 3.x → 4.x
```

under an old parent dependency.

That could have introduced an incompatible major-version change.

## Resolution

The parent was upgraded instead:

```bash
yarn up -R @backstage/backend-defaults
```

The resulting dependency chain became:

```text
@backstage/backend-defaults 0.17.8
└── infinispan 0.13.0
    └── urllib 4.9.1
```

## Lesson

When a transitive vulnerability requires a major-version jump, upgrade the owning parent dependency where possible.

# 15. Yarn Referenced a Missing got Patch

## Symptom

An attempted Backstage CLI upgrade failed with:

```text
got@patch:got@npm%3A11.8.2#~/.yarn/patches/got-npm-11.8.2-c1eb104558.patch:
ENOENT: no such file or directory
```

## Investigation

The repository did not contain:

```text
.yarn/patches/got-npm-11.8.2-c1eb104558.patch
```

and the reference was not present in the project manifest.

## Local State Cleanup

Yarn's local install state was removed:

```bash
rm -f .yarn/install-state.gz
yarn install --immutable
```

This successfully regenerated normal install state.

However, the broad CLI upgrade still required the unavailable patch.

## Decision

The broad CLI upgrade was abandoned.

Security issues were instead remediated using focused package upgrades and explicit resolutions.

## Lesson

Do not create a guessed patch simply to satisfy the package manager.

If a broad dependency upgrade introduces repository-specific patch requirements, a smaller and safer remediation may be preferable.

# 16. tar Vulnerabilities

## Finding

Trivy discovered several vulnerable `tar` versions.

Inspection showed multiple sources:

```text
npm bundled tar
application tar
node-gyp / cacache tar
Backstage tar
```

## First Remediation

Compatible copies were upgraded:

```bash
yarn up -R tar
```

The main production dependency resolved to:

```text
tar@7.5.22
```

## Remaining Old tar 6.x

Further inspection found that `node-gyp` was declared directly as a backend runtime dependency.

The chain brought old build tooling into the production install.

## Resolution

`node-gyp` was moved from:

```json
"dependencies"
```

to:

```json
"devDependencies"
```

The production image was rebuilt and inspected:

```bash
docker run \
  --rm \
  --entrypoint sh \
  backstage-portal:ci \
  -c '
    find /app/node_modules \
      -type f \
      -path "*/tar/package.json" \
      2>/dev/null
  '
```

The final production application contained:

```text
/app/node_modules/tar/package.json
version 7.5.22
```

## Lesson

Build-time dependencies should not be shipped as runtime dependencies unless the application genuinely needs them after startup.

# 17. npm and npx Added Unnecessary Production Attack Surface

## Finding

The Node base image included npm's own dependency tree:

```text
/usr/local/lib/node_modules/npm/
```

Trivy found vulnerable packages inside that tree even though Backstage does not use npm to run in production.

## Resolution

The production image removes npm and npx after dependency installation:

```dockerfile
USER root

RUN rm -rf /usr/local/lib/node_modules/npm \
    && rm -f /usr/local/bin/npm /usr/local/bin/npx

USER node
```

## Validation

```bash
docker run \
  --rm \
  --entrypoint sh \
  backstage-portal:ci \
  -c '
    node --version
    id

    if command -v npm >/dev/null 2>&1; then
      exit 1
    else
      echo "npm not present"
    fi
  '
```

## Result

The runtime retained Node.js while unnecessary package-manager tooling was removed.

## Lesson

The production image should contain only what is required to run the application.

Reducing tools reduces attack surface.

# 24. basic-ftp Required a Targeted Major-Version Resolution

## Finding

The final remaining Trivy finding was:

```text
basic-ftp 5.3.1
```

introduced by:

```text
get-uri 6.0.5
└── basic-ftp ^5.0.2
```

The security fix existed in `basic-ftp 6.2.1`.

## First Attempt

A resolution targeting the resolved package:

```json
"basic-ftp@npm:5.3.1": "npm:6.2.1"
```

did not take effect.

`yarn why basic-ftp` still showed:

```text
basic-ftp@5.3.1
```

## Root Cause

The dependency descriptor requested by `get-uri` was:

```text
basic-ftp@npm:^5.0.2
```

The resolution selector did not match the dependency request as intended.

## Resolution

A package-wide root resolution was used:

```json
"resolutions": {
  "basic-ftp": "npm:6.2.1"
}
```

## Compatibility Validation

Because this crossed a major version boundary, the parent module was explicitly tested:

```bash
node --input-type=module <<'EOF_NODE'
import('get-uri')
  .then(() => console.log('get-uri compatibility check passed'))
  .catch(error => {
    console.error(error);
    process.exit(1);
  });
EOF_NODE
```

The normal Backstage validation suite was also run afterward.

## Lesson

Major-version dependency overrides should be exceptional.

When they are required for security, validate the immediate parent and then run the entire build/test pipeline.

# 25. Full Dependency Security Validation

Instead of relying only on the formatted Trivy table, a JSON report was generated:

```bash
trivy image \
  --severity HIGH,CRITICAL \
  --ignore-unfixed \
  --format json \
  backstage-portal:ci \
  > /tmp/backstage-trivy.json || true
```

A short Python script was then used to summarize unique findings:

```python
import json

with open("/tmp/backstage-trivy.json") as f:
    data = json.load(f)

rows = set()

for result in data.get("Results", []):
    for vulnerability in result.get("Vulnerabilities") or []:
        rows.add(
            (
                vulnerability.get("PkgName", ""),
                vulnerability.get("InstalledVersion", ""),
                vulnerability.get("FixedVersion", ""),
                vulnerability.get("Severity", ""),
            )
        )

for row in sorted(rows):
    print(row)
```

This made remediation faster by exposing the complete remaining list at once.

# 26. Final Production Container Security Result

The final image was scanned with:

```bash
trivy image \
  --severity HIGH,CRITICAL \
  --ignore-unfixed \
  --exit-code 1 \
  backstage-portal:ci
```

The command exited:

```text
0
```

The scan reported no remaining HIGH or CRITICAL findings.

This was confirmed with:

```bash
echo $?
```

Result:

```text
0
```

## Key Point

The vulnerability gate was not weakened.

We did not change:

```text
severity: HIGH,CRITICAL
exit-code: 1
```

to make CI pass.

Instead, the underlying dependency and runtime issues were remediated until the original security policy passed.

# Engineering Principles Reinforced

The issues encountered in this project reinforced several platform engineering practices:

1. secure defaults should be encoded into golden paths
2. development authentication and production authentication should be separated
3. authentication and authorization solve different problems
4. default allow-all authorization is not a production security model
5. catalog metadata requires semantic validation, not only valid YAML
6. functional tests do not replace vulnerability scanning
7. container images should run as non-root
8. build-time tooling should not automatically become runtime tooling
9. unnecessary package managers should be removed from production images
10. operating-system packages matter to container security
11. parent dependencies should be upgraded before forcing incompatible transitive versions
12. recursive dependency upgrades are preferable when semver already permits patched versions
13. targeted resolutions should be documented and validated
14. major-version overrides require explicit compatibility testing
15. CI security gates should not be weakened merely to obtain a green build
16. machine-readable scanner output improves vulnerability remediation
17. every fix should be followed by reproducible validation
18. troubleshooting history is valuable engineering documentation
19. developer portals should enforce platform standards, not simply display information
20. platform engineering is as much about safe defaults and feedback loops as it is about infrastructure
